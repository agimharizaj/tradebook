# Tradebook vs industry standards - review, July 2026

This review compares the Tradebook codebase against what commercial trading journals, established position-size calculators, and general web engineering practice look like in 2026. It reads the actual source, not the docs, and it distinguishes between gaps that matter for a single-user MVP today and gaps that only matter at scale. File references are to the repo at `/Users/agimharizaj/Desktop/TradingBuddy`.

## Executive verdict

Tradebook is a genuinely good solo MVP. The database layer is the strongest part: Row Level Security is complete and correctly written for every table and the storage bucket, no service-role key exists anywhere in the project, and the auth plumbing follows the current Supabase SSR reference pattern almost line for line. The risk calculator math is correct, which is the single most important correctness claim in the app, and I verified it against the Babypips and Myfxbook methodologies rather than taking it on faith. The dashboard already computes profit factor and renders an equity curve, which puts it ahead of many hobby journals.

The real gaps are smaller than you might fear but they are concrete. The password minimum of 6 characters is below the industry floor of 8. The dim text color fails WCAG AA contrast everywhere it is used, and so does the white-on-violet primary button text. The journal deletes trades with a single click and no confirmation, which is a data-loss trap in a tool whose whole point is preserving your history. The "Expectancy" metric in the journal is mislabeled: it computes an average R-multiple, not expectancy as the industry defines it. The PWA manifest points at an SVG when Chrome's installability checklist wants 192 and 512 pixel PNGs, and both PNGs already sit unused in `public/`. And there is no drawdown metric anywhere, which is the one headline analytic every commercial journal ships that Tradebook does not.

None of these are architectural. Every item above is a small, contained fix. The verdict is: solid foundation, correct core math, and a short punch list of finish-quality issues, most of them fixable in an afternoon each.

## How Tradebook compares to commercial trading journals

The commercial baseline in 2026 is set by TradeZella, Edgewonk, TraderSync, Tradervue, and at the free end Stonk Journal. The consensus feature set across them is: automated broker import (TraderSync advertises 700+ brokers, TradeZella 500+, Edgewonk 200+ via CSV), per-trade records with setup tags, R-multiple, screenshots, and emotion or psychology tracking (Edgewonk's Tiltmeter is the best-known example), and an analytics layer built on win rate, average win and loss, expectancy, profit factor, equity curve, and drawdown, sliced by setup, symbol, day, and hour. The newer differentiators are AI review (TradeZella's Zella AI, TraderSync's Cypher), backtesting, and prop-firm tracking. Sources: [TradeZella's Edgewonk comparison](https://www.tradezella.com/blog/edgewonk-vs-tradezella), [Tradeciety's 2026 journal roundup](https://tradeciety.com/best-online-trading-journals), [TradeTrakR's side-by-side](https://tradetrakr.com/blog/posts/tradersync-vs-edgewonk-vs-tradezella).

Against that baseline, the Tradebook data model in `supabase/migrations/0001_init.sql` (lines 89 to 106) covers most of the core journaling fields: pair, direction, date, entry, stop, exit, size in lots, PnL, R-multiple, an emotion field, free notes, and a link to a strategy. That is a respectable subset. The emotion field being a free-text string rather than a constrained tag list means it can never be aggregated ("Calm" vs "calm" vs "chill" are three different values), which is the difference between having the field and having the analytic. The strategy link is the app's equivalent of setup tagging and it works, but there is exactly one dimension of it, where commercial journals let you stack tags (setup, mistake, market condition) and then report by each.

The MT5 import in `src/components/journal/ImportTradesModal.tsx` deserves specific praise. It parses both CSV and MT5 HTML reports, auto-detects delimiters, auto-maps columns with manual override, folds commissions and swap into net PnL (line 143), and deduplicates re-imports by broker ticket via the `ext_id` column added in `supabase/migrations/0002_trade_import.sql`. That is a real broker-import pipeline, scoped sensibly to the one broker format you actually use. For a single-user MVP this is the right call versus chasing 700 brokers.

The measurable gaps against the commercial set are these. First, there are no per-trade screenshots; the `entry-models` bucket serves strategy documentation only, while every commercial journal treats the chart screenshot as a first-class trade field. Second, `traded_on` is a date, not a timestamp, so time-of-day and session analytics (a standard report in all five products) are structurally impossible until the column changes. Third, commissions are merged into PnL at import rather than stored separately, so you can never answer "how much did fees cost me this month". Fourth, and most visibly, there is no drawdown figure anywhere: I grepped the source and the word does not appear. The dashboard in `src/app/(app)/dashboard/page.tsx` already builds the running equity array (lines 44 to 46), so maximum drawdown is about four lines away from existing. Every commercial journal shows it, and for a prop-firm trader (the profile page literally has an FTMO placeholder) drawdown is the metric that gets accounts breached.

Finally, the "Expectancy" card in `src/components/journal/JournalWorkspace.tsx` (line 48) computes the mean of whatever R-multiples were manually entered, over only the trades that have one. The industry definition is win rate times average win minus loss rate times average loss, computed over all closed trades ([P&L Ledger's expectancy guide](https://www.pnlledger.com/expectancy-r-multiples-the-plain-english-guide/), [LiquidityFinder on journal metrics](https://liquidityfinder.com/news/trading-journal-metrics-expectancy-drawdowns-and-r-multiples-explained-fc2af)). Average R and expectancy converge only if every trade has an accurate R recorded, which manual entry does not guarantee. Either rename the card to "Avg R" or compute true expectancy from the PnL columns; showing the wrong number under the right label is worse than not showing it.

## Risk calculator correctness review

This is the section where I went looking for bugs and mostly did not find them. The engine lives in `src/app/(app)/risk/page.tsx`. The core formula at lines 139 and 149 is: pip value in account currency = pip size times contract size times conversion rate, then lots = risk amount divided by (stop distance in pips times pip value). Worked example: 10,000 USD account, 1 percent risk, EUR/USD, 50 pip stop gives risk of 100, pip value of 0.0001 times 100,000 times 1 = 10 dollars, so 0.2 lots. That matches the Babypips reference method exactly ([Babypips: Calculating Your Position Sizes](https://www.babypips.com/learn/forex/calculating-your-position-sizes), [Babypips calculator](https://www.babypips.com/tools/position-size-calculator)). The conversion direction is also correct: when the quote currency differs from the account currency, the client fetches quote-to-account (line 81), which is the rate you multiply pip value by. This is the step hobby calculators most often get backwards, and Tradebook gets it right.

Pip and contract conventions (lines 19 to 28): 0.0001 for standard pairs, 0.01 for JPY pairs, and 100,000 contract size are all standard. For gold the app uses pip 0.1 with a 100 ounce contract, giving 10 dollars per pip per lot. Myfxbook defines the XAU/USD pip as 0.01, giving 1 dollar per pip ([Myfxbook XAUUSD pip calculator](https://www.myfxbook.com/forex-calculators/pip-calculator/XAUUSD)); other calculators use 0.1 or even 1.0, because there is genuinely no industry consensus on what a gold "pip" is. The important point is that the sizing math is invariant to this choice: stop distance in pips is price distance divided by pip, pip value is pip times contract, and the pip term cancels, so the lot size output is correct under any convention. Verified numerically: a 10 dollar stop on gold at 1 percent of a 10,000 account yields 0.1 lots (10 oz) under both the 0.1 and 0.01 conventions. Only the displayed "Stop distance ... pips" row differs from Myfxbook by a factor of ten, which merits a one-line hint in the UI, nothing more. BTC with pip 1 and contract 1 sizes positions directly in coins against price distance, which is the sane way to handle crypto.

The FX route in `src/app/api/fx/route.ts` is well built: Frankfurter for fiat with 5 minute revalidation, CoinGecko for BTC with a USD-then-convert fallback, gold-api.com for XAU with the same fallback pattern, and clean 400/502 error responses. Two honest caveats. Frankfurter serves ECB reference rates published once per business day, so the conversion rate can be nearly 24 hours stale and is frozen over weekends; for position sizing this drift is a fraction of a percent of risk and the UI already discloses the date (line 308 of the risk page), so this is acceptable, but it should stay disclosed. Second, `CLAUDE.md` still says "Gold (XAU) stays manual" while the code fetches it live, so the project memory has drifted from reality.

The remaining gaps against Myfxbook and Babypips conventions are refinements, not errors. The output rounds with `toFixed(2)` (line 156), which rounds to the nearest 0.01 lot and can therefore round up, sizing you at slightly more than the stated risk; broker-grade calculators floor to the lot step instead. There is no minimum lot or step validation, and no margin or required-leverage output, which Myfxbook includes. The account currency field is free text, so a typo like "USDD" silently produces a failed conversion with a manual-entry fallback message, which is handled but could be caught earlier. All of these are polish items on top of a correct engine, and correctness is the part that cannot be retrofitted.

## Design and accessibility review

The visual system holds up well against how trading platforms actually design in 2026. The brand rationale in `design/tradebook-brand-concept.html` and `CLAUDE.md` (no pure black, blue-charcoal elevation ladder, one accent, monospace numerals) matches what TradingView and institutional terminals do: muted dark surfaces rather than #000, restrained accent color, and crisp numeric legibility for long sessions. The implementation in `src/app/globals.css` is faithful to it, the elevation ladder (sidebar #161A23, canvas #1C212C, card #222834, input #2B3240) is applied consistently, and JetBrains Mono is applied to every number I checked across the dashboard, journal, calculator, and import preview. Fonts load through `next/font` with proper CSS variables in `src/app/layout.tsx`. This is more design discipline than most solo MVPs ever get.

The contrast numbers are where it breaks. I computed WCAG ratios for the actual palette. Body text #E7E9EF on card is 12.2:1, comfortably passing. Muted #9AA0B0 passes at 5.7:1 on card and 6.7:1 on the page background. But dim #757C8E measures 3.5:1 on card, 3.1:1 on the input surface, and 3.9:1 on the content canvas, all below the 4.5:1 AA minimum for normal text ([WCAG 2.1, contrast minimum](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html)). Dim is not decorative: it is the color of every form label (`Field` components in the risk page line 346, journal line 482, profile line 341), calendar day numbers, and hints, always at extra-small sizes where contrast matters most. The other failure is white text on the violet accent #7C6CFF at 3.9:1, which is every primary button in the app at 14px text. Lightening dim toward the muted value and either darkening the accent or switching button text to a near-black would clear both. The success and danger colors pass (7.6:1 and 5.1:1 on card), so PnL coloring is fine.

Interaction accessibility is partial. Inputs have proper visible focus rings via the `.field:focus` styles. Icon-only buttons mostly carry `aria-label`s (journal close and delete, sidebar collapse). But the modals in the journal, import, and strategy views are plain fixed-position divs with no `role="dialog"`, no `aria-modal`, no focus trap, and no Escape-to-close. The SVG charts on the dashboard have no accessible name or text alternative at all. And `src/app/layout.tsx` line 22 sets `maximumScale: 1`, which disables pinch zoom and fails WCAG 1.4.4; on a "mobile-friendly" app this should simply be removed. Touch targets are mostly fine (the bottom nav items in `src/components/MobileNav.tsx` comfortably exceed 44px), but the trade delete button in the day modal is a bare 14px "✕" character, well under any touch-target guideline, and it fires the delete with no confirmation.

On PWA readiness: `src/app/manifest.ts` declares only `/icon.svg` for both `any` and `maskable` purposes, while Chrome's installability criteria want 192 and 512 pixel PNG icons declared in the manifest ([MDN, Making PWAs installable](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable), [web.dev manifest guide](https://web.dev/learn/pwa/web-app-manifest)). The PNGs already exist at `public/icon-192.png` and `public/icon-512.png`; they are just not referenced. There is also no service worker, so the app has no offline behavior and will show a browser error page when the connection drops. For a later PWA phase that is fine, but the manifest icon fix costs five minutes now.

## Engineering and security review

The security posture is the best part of the codebase. The RLS block in `supabase/migrations/0001_init.sql` (lines 124 to 150) loops over all seven tables and creates select, insert, update, and delete policies scoped to `auth.uid()`, with `with check` on both insert and update, which is the complete and correct pattern; partial policy coverage is the classic Supabase mistake and it is not made here. The storage policies (lines 161 to 175) scope objects to a folder named after the user id for read, write, and delete. The `0002` migration adds a column to an already-protected table, so it inherits coverage. No service-role key appears anywhere in the source or env examples; only `NEXT_PUBLIC_` variables reach the client, exactly as the architecture rules demand. Auth is checked twice, in `src/lib/supabase/middleware.ts` via `getUser()` (the secure call, not `getSession()`) and again in the `(app)` layout, which is sensible defense in depth. The password-change flow in `ProfileForm.tsx` re-verifies the current password before updating, which many apps skip.

The one genuine security gap is password policy. Both `AuthForm.tsx` (line 144) and `ProfileForm.tsx` (line 114) enforce a 6 character minimum, matching Supabase's default. Current NIST guidance sets 8 characters as the absolute floor and, in the 2025 revision, 15 for password-only authentication ([NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)); Supabase's own documentation recommends at least 8 and preferably 12+, plus enabling HaveIBeenPwned leaked-password protection in the dashboard ([Supabase password security](https://supabase.com/docs/guides/auth/password-security)). Note that the HTML `minLength` attribute is cosmetic; the real enforcement is the dashboard Auth setting, which is still at its default of 6. Since Google SSO exists as the strong path, this is a ten-minute fix: raise the dashboard minimum to 10 or 12, update the two client checks to match, and toggle leaked-password protection if the plan allows it. The unauthenticated `/api/fx` proxy is technically an open relay to three third-party APIs with no rate limit; for a single-user app on Vercel this is a non-issue today, and I flag it only so it is a known decision.

Code quality is decent but has three recurring habits worth breaking. First, read errors are silently swallowed: `JournalWorkspace.tsx` line 68 and `dashboard/page.tsx` line 20 destructure `{ data }` and ignore `error`, so a failed query renders indistinguishably from "no trades yet", which in a journal is an actively misleading state (write paths, to their credit, do handle errors). Second, the input-styling CSS block (`.field` / `.jfield` / `.input`) is copy-pasted into inline `<style>` tags in four separate components; it belongs in `globals.css` once. Third, `StrategyWorkspace.tsx` is a 930 line single client component handling list state, drafts, uploads, drag-reorder, and three modal states; it works, but it is at the size where every future change risks breaking an unrelated feature, and splitting the editable-list and image-uploader pieces out would pay for itself quickly. Related smaller items: journal numeric fields pass raw `Number(v)` with no validation so "abc" silently becomes null in the database, there are no generated Supabase types (`supabase gen types typescript`) so every query result is hand-cast with `as`, and there are zero automated tests, which matters mainly for one file: the risk math in `risk/page.tsx` is pure-function-shaped and would take an hour to cover with a handful of unit cases that lock its correctness in forever. Finally, timezone handling is loose: `traded_on` defaults to the UTC date server-side while the calendar keys off local dates, so trades logged near midnight can land on the neighboring day.

## What is fine to defer (MVP context)

A large share of the distance to TradeZella is distance you should not try to close now. Automated multi-broker sync is a business, not a feature; the MT5 import covers the one broker in use. AI trade review, backtesting, trade replay, and prop-firm dashboards are the commercial products' upsell tier, not their core. MFE/MAE tracking requires intraday data the app does not ingest. Margin and leverage outputs on the calculator are nice-to-have while the sizing itself is correct. Rate limiting and abuse protection on `/api/fx` matter only if the app ever gets a second user. A service worker and offline mode belong to the explicitly deferred PWA polish phase. CSP headers, monitoring, and CI pipelines are scale concerns for a not-yet-deployed single-user app. Multi-tag setups and time-of-day analytics are worth doing eventually, but only the schema decision (timestamp instead of date, separate commission column) is urgent, because schema is the one thing that gets more expensive to change the longer trade history accumulates. Change the columns now, build the reports later.

## Prioritised gap list

1. Raise the password minimum from 6 to at least 10 in the Supabase dashboard and in `AuthForm.tsx:144` and `ProfileForm.tsx:114`, and enable leaked-password protection if the plan allows. This is the only item on the list that is a real security exposure.
2. Add a confirmation step to trade deletion in `JournalWorkspace.tsx:131`. A one-tap irreversible delete of journal history, from a tiny touch target, is the most likely way you lose data this year.
3. Fix the journal "Expectancy" metric (`JournalWorkspace.tsx:48`) to either compute true expectancy from PnL or honestly relabel as "Avg R". A journal that shows a wrong headline metric undermines trust in every other number.
4. Fix the two AA contrast failures: lighten `--dim` (#757C8E, 3.1 to 3.9:1 in use) in `globals.css:10` and fix white-on-accent button text (3.9:1). Long-session legibility is the entire justification for the dark theme.
5. Add max drawdown to the dashboard; the equity array at `dashboard/page.tsx:44-46` already exists, so this is a few lines for the one standard analytic the app is missing.
6. Change `trades.traded_on` to a timestamp and store commissions in their own column via a new migration, before imported history grows; these are the only gaps that get more expensive with time.
7. Point the PWA manifest (`src/app/manifest.ts`) at the existing `icon-192.png` and `icon-512.png` so Chrome installability criteria are met, and remove `maximumScale: 1` from `layout.tsx:22`.
8. Surface Supabase read errors in the journal and dashboard instead of rendering silent empty states.
9. Floor the calculator's lot output to the 0.01 step instead of `toFixed(2)` rounding (`risk/page.tsx:156`), and add a one-line note on the gold pip convention.
10. Add unit tests for the risk math, split `StrategyWorkspace.tsx`, move the duplicated field CSS into `globals.css`, and update the stale `CLAUDE.md` claims (gold is live, signup does collect a name). None of this changes behavior; all of it lowers the cost of every future change.
